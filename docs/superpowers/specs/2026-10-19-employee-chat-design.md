# 직원에게 직접 말 걸기 (1:1 대화 + 빠른 수정) — 설계

- 날짜: 2026-10-19
- 상태: 초안 (대표 검토 대기)
- 관련: 기존 "이어서 지시"(parentSessionId), ambient-chat, 볼트 회상, AgentDetailPanel

## 1. 의도와 이유

지금 대표는 지시를 내린 뒤 산출물이 나올 때까지 지켜보기만 하고, 직원 곁에 가도 NearbyCard 로 상태만 볼 수 있다.
산출물에 궁금한 점(근거·판단 이유)이 있거나 작은 부분만 고치고 싶어도 "이어서 지시"로 7개 부서 파이프라인 전체를 다시 돌려야 한다 (Ollama 기준 수 분, LLM 10~20회).

이 기능은 **오피스에서 담당 직원에게 걸어가 직접 묻고, 그 자리에서 고치게 하는 경험**을 만든다. 메타버스 오피스라는 컨셉을 실제 업무 가치로 연결하는 것이 핵심이다.

## 2. 목표 / 비목표 / 안티 목표

### 목표 (대표 결정)
- **업무 질문 위주, 사담도 가능** — 직원은 자기가 맡은 업무 맥락(산출물, 계획상 자기 과제, 받은 지적, 볼트 기억)을 근거로 자기 말투로 답한다. 업무 외 말에는 성격대로 짧게 받아준다.
- **대화가 실제 산출물 수정으로 이어진다** — "그 부분 고쳐줘" → 직원이 수정안 제시 → 대표 승인 → 산출물 반영. (B안: 그 직원이 직접 빠르게, LLM 1~2회)
- **원본 덮어쓰기 + 되돌리기** — 새 세션/버전을 만들지 않고 현재 산출물을 갱신하며, 되돌리기 버튼을 제공한다.
- **오른쪽 사이드 패널 UI** (목업 B안) — 기존 상세 패널 자리에 대화창. 대화 기록 + 수정안 카드(삭제=빨강 취소선, 추가=초록) + [승인][다시][산출물 전체 보기].
- **지난 대화를 기억한다** — 다음 날·다른 세션에서 다시 말을 걸어도 그 직원은 대표와의 이전 대화를 안다.

### 비목표
- 교차검토·QA 를 거치는 정식 재작업 (그건 기존 "이어서 지시"의 몫)
- 직원끼리 대화하게 만들기, 음성, 다자 채팅방
- 대화창이 열려 있다고 자동으로 말을 거는 기능 (LLM 은 대표가 보낼 때만 호출)

### 안티 목표 (이러면 실패)
- 승인 없이 산출물이 바뀐다.
- 직원이 근거 없이 지어낸 수치·출처로 답하거나 고친다 (모르면 모른다고 해야 한다).
- 대화 기능이 하루 LLM 예산을 조용히 갉아먹어 정작 지시가 429 로 실패한다.
- 되돌릴 수 없는 수정이 생긴다.

## 3. 제약

- 레이어 규칙 (README): Controller=입출력/DTO, Service=도메인, Repository=영속화, Formatter=직렬화, Provider=외부 API. 프론트는 `services/`에서만 fetch.
- 공유 타입은 `shared/src/*.d.ts` (런타임 코드 없음).
- 모든 LLM 호출은 `LlmService` 경유 (RateLimiter·일일 예산·Abort 적용). 기본 로컬 모델은 `qwen3:8b` — **8B 모델이 큰 JSON/긴 문서 재작성에 약하다**는 기존 교훈(BuildPhase: 내용은 코드펜스, 메타만 작은 JSON)을 따른다.
- 세션 영속화는 `node:sqlite` (`SESSION_DATABASE_PATH`, `SessionRepository`). 산출물은 `sessions.result_json`(Deliverable JSON), 코드형 파일은 `workspace/<folder>/`, 문서는 볼트에도 저장된다.
- 변경 API 는 `AdminMutationGuard` 를 반드시 적용한다 (보안 감사 MEDIUM-2: ambient-chat 이 가드 밖이었던 실수를 반복하지 않는다).
- 웹사이트 산출물 수정 후에는 기존 `website-lint` 를 다시 돌린다.

## 4. 대표가 정한 동작 (확정)

### 4.1 대화 흐름
1. 대표 아바타가 직원 곁(90px)에서 `F` → NearbyCard 에 **"말 걸기"** 버튼.
2. 오른쪽 패널에 그 직원 대화창이 열린다 (헤더: 부서 배지·이름·상태 / 본문: 대화 기록 / 하단: "○○에게 말하기…" 입력).
3. 대표 메시지 → 직원 답변. 답변은 둘 중 하나:
   - **일반 답변** (텍스트)
   - **수정안** — "이렇게 바꾸겠습니다" 요약 + 변경 미리보기 + [승인][다시][산출물 전체 보기]
   - (변형) **담당 밖 안내** — "그건 디자인팀 담당입니다" / **전체 회의 제안** — 여러 부서에 걸친 큰 수정이면 "이어서 지시"를 제안하고, 대표가 누르면 대화 요약이 채워진 이어서 지시 입력창으로 연결.
4. [승인] → 산출물 덮어쓰기 → "✓ 산출물 수정됨 · 되돌리기" 토스트, 산출물 패널에도 되돌리기 버튼.
5. [다시] → 수정안 폐기, 대화 계속 (대표가 추가 지시 가능).

### 4.2 대화 상대 (대표 결정)
- **24명 전원**(팀장 8 + 팀원 16)과 대화할 수 있다. NearbyCard 의 "말 걸기"는 모든 직원에게 보인다.
- **기억은 사람마다 따로** — 키는 `agent_id`. 같은 부서라도 팀장과 팀원은 서로의 대화를 모른다.
- 팀원도 자기 부서 범위 안에서 수정안을 낼 수 있다.
- **비서실장(`chief`)은 직접 고치지 않는다.** 전체를 아는 검수 담당으로서 답변하고, 수정 요청에는 "○○팀 △△에게 말씀하세요"(redirect) 또는 이어서 지시(escalate)로 안내한다.

### 4.3 수정 범위
- 산출물에는 부서별 원고가 따로 남지 않으므로 **최종 산출물을 직접** 고친다.
  - document / slides: `Deliverable.body` 중 해당 부분
  - website: 관련 파일(`artifacts[]` + `workspace/` 실제 파일)만
- 직원은 **자기 전문 영역 안에서만** 고친다. 영역 밖 요청은 담당 부서를 안내.
- *(내 판단)* 범위 강제는 **프롬프트 + 대표 승인**으로 충분하다고 본다. 서버가 본문 구간↔부서를 강제하려면 통합 단계 변경이 필요해 과하다.
- *(내 판단)* 그 세션에 **참여한 부서**(plan.assignments / team)의 직원만 수정안을 낼 수 있다. 미참여 직원은 답변만 하고, 수정 요청엔 참여 부서를 안내한다. 서버도 approve 시 이를 검사.

### 4.4 기존 NearbyCard 버튼 (대표 결정)
- 기존 "보고 요청"·"일상 대화" 버튼(지시 문구를 채워 전체 파이프라인을 돌림, LLM 10~20회)은 **"말 걸기" 하나로 대체**한다.
- "보고 요청"은 대화창 안의 **빠른 질문 버튼**("지금 진행 상황 알려줘")으로 옮긴다 — 누르면 그 문장이 대표 메시지로 전송된다(LLM 1회).
- 이 버튼들이 쓰던 `onSelectBrief` 경로는 NearbyCard 에서 더 쓰이지 않으면 함께 정리한다(다른 호출부가 있으면 유지).

### 4.5 저장 방식
- 승인된 수정은 현재 산출물을 덮어쓴다 (`result_json`, 볼트 산출물 노트, workspace 파일 모두 일관되게).
- 이전 상태는 **수정 이력 스택**으로 보관하고 한 단계씩 되돌린다.

### 4.6 기억
- 대화 기록은 **직원(사람) 단위로 세션을 넘어** 남는다. 다른 세션 산출물을 보고 있어도 그 직원은 이전 대화를 안다.

## 5. 제안 설계 (빌더 재량 포함)

### 5.1 데이터 (SQLite, 기존 sessions.sqlite 에 테이블 추가)
```
agent_chat_messages(id, agent_id, session_id NULL, role 'ceo'|'agent', kind 'text'|'proposal'|'redirect'|'escalate',
                    text, proposal_id NULL, created_at)
deliverable_revisions(id, session_id, agent_id, chat_message_id, summary,
                      before_json, after_json, status 'applied'|'reverted', created_at)
agent_chat_proposals(id, session_id, agent_id, summary, patch_json, status 'pending'|'approved'|'discarded', created_at)
```
- `before_json/after_json` 은 바뀐 범위만이 아니라 **Deliverable 스냅샷**(+ 코드형이면 바뀐 파일 내용)을 저장 — 되돌리기를 단순·확실하게. 산출물은 수십 KB 수준이라 용량 문제 없음.

### 5.2 기억 구성 (프롬프트 컨텍스트)
- 그 직원의 **최근 대화 N턴**(예: 12) 원문 + 그보다 오래된 대화의 **롤링 요약** 1개(직원별 저장, 일정 턴마다 갱신).
- 현재 세션 맥락: 브리프, 계획상 그 부서 과제, 리뷰 지적 중 그 부서 관련, 산출물 본문(길면 자르거나 관련 구간 위주).
- 볼트 회상: `VaultService.recall(질문)` 상위 몇 건. **선행 조건: 코드 리뷰 #4(회상 임계값 스케일 오류) 수정** — 안 고치면 무관한 기억이 근거로 섞인다.
- 볼트에도 남긴다: 승인된 수정은 프로젝트 폴더에 "수정 기록" 노트(누가·왜·무엇을), 대화 요약은 직원 지식 노트에 추가 — 회사의 기억이 앱 밖(Obsidian)에서도 보이도록.

### 5.3 LLM 호출 설계
- **턴 1회 = 의도 판별 + 답변** 을 작은 JSON 으로: `{"type":"answer"|"propose"|"redirect"|"escalate","reply":"...","target":"..."}`
- `propose` 일 때만 **2번째 호출**로 실제 수정 내용 생성:
  - 문서/슬라이드: 문서 전체 재작성 대신 **교체할 원문 구간 + 새 구간**(find/replace 쌍, 코드펜스로 받음)을 받아 적용. 원문 구간이 정확히 일치하지 않으면 실패 처리 후 "다시" 유도.
  - 웹사이트: 대상 파일을 하나씩 코드펜스로 전체 재작성(BuildPhase 와 같은 방식, 파일당 호출 1회) → website-lint. *(내 판단)* 여러 파일 수정 허용(`patch_json` 은 파일 배열), 단 3개 초과면 escalate. **수정안 생성 시점에 lint** 를 돌려 오류가 있으면 카드에 표시하고 [승인]을 비활성화, [다시]를 유도.
- 진행 중 세션에서는 `propose` 를 허용하지 않고 "세션이 끝나면 고칠게요"로 답하도록 프롬프트·서버 양쪽에서 막는다.

### 5.4 API (모두 `/api` 하위, 변경 API 는 AdminMutationGuard)
- `GET  /agents/:id/chat?sessionId=` — 대화 기록 (페이지네이션)
- `POST /agents/:id/chat` `{ sessionId, text }` — 대표 메시지 → 직원 답변(+수정안)
- `POST /chat/proposals/:id/approve` — 산출물 반영, revision 생성
- `POST /chat/proposals/:id/discard`
- `POST /sessions/:id/revisions/undo` — 최근 applied 수정 1건 되돌리기
- `GET  /sessions/:id/revisions` — 수정 이력
- 응답은 동기 JSON (스트리밍 불필요 — 답변이 짧음). 로딩 중 패널에 "○○ 팀장이 생각 중…" 표시. 취소 가능(AbortSignal).

### 5.5 백엔드 구성 (새 모듈 `chat/` 제안)
- `AgentChatController` / `AgentChatService`(대화·의도·수정안 생성) / `DeliverableRevisionService`(적용·되돌리기, result_json·볼트·workspace 일관 갱신) / `AgentChatRepository`(SQLite).
- 산출물 덮어쓰기는 `SessionRepository` 에 "결과 갱신" 메서드를 추가해서 수행 (직접 SQL 분산 금지).

### 5.6 프론트
- `NearbyCard` 액션에 "말 걸기" 추가 → store 에 `chatAgentId` 설정.
- 새 `AgentChatPanel` (오른쪽 패널, AgentDetailPanel 과 같은 슬롯; 동시에 하나만).
- `ProposalCard` — diff 표시(문서: 단어 단위 하이라이트, 웹: 파일명 + 변경 줄 요약), 버튼 3개.
- 승인 후 store 의 현재 deliverable 갱신(세션 상세 재조회) + 토스트(되돌리기 포함). 산출물 패널(DeliverablePanel/ArtifactPanel)에 "되돌리기"와 "수정 이력 n건".
- 웹사이트 미리보기 iframe 은 수정 후 캐시 무효화(쿼리스트링) 로 새로고침.

### 5.7 예산 *(내 판단)*
- 대화 호출은 공용 일일 예산에 집계하되, **대화 전용 하루 상한**(`CHAT_DAILY_CALL_LIMIT`, 기본 60)을 따로 둔다.
- **지시용 예비분 보장**: 공용 예산 잔여가 `CHAT_BUDGET_RESERVE`(기본: 일일 한도의 25%) 이하이면 대화를 거절한다 → 대화가 지시 파이프라인을 굶기지 않는다(안티 목표 3).
- 구현: `LlmService.complete*` 옵션에 호출 출처(`purpose: 'workflow' | 'chat' | 'ambient'`)를 추가하고 `LlmBudgetService` 가 출처별 카운트·검사. `/api/config` 의 `llmBudget` 에 대화 사용량 추가, 패널에 소진/거절 안내.

3. (같은 묶음 권장) 자율 세션 타임아웃 크래시(`autonomous-work.service.ts:177-180`), 볼트 노트 읽기 범위 제한(`vault.repository.ts:167-172`), `/workspace` CSP sandbox 헤더.

## 7. 수용 기준
- 직원 곁 F → 말 걸기 → 오른쪽 패널에 그 직원 대화창, 이전 대화가 보인다 (서버 재시작 후에도).
- 업무 질문에 그 부서 산출물·과제를 근거로 답한다. mock 프로바이더로 E2E 가능.
- "고쳐줘" → 수정안 카드 → 승인 시 `GET /sessions/:id` 결과, 볼트 산출물 노트, (웹이면) workspace 파일이 모두 바뀐다.
- 되돌리기 → 세 곳 모두 직전 상태로 복원. 연속 2회 수정 후 2회 되돌리기 = 원본.
- 진행 중 세션에서는 수정안이 나오지 않는다 (서버가 approve 를 409 로 거절).
- 담당 밖 요청 → redirect 응답, 여러 부서 수정 → escalate 응답 + 이어서 지시로 연결.
- NearbyCard 에 "보고 요청"·"일상 대화"가 사라지고 "말 걸기"가 있다. 대화창의 빠른 질문 버튼은 파이프라인을 돌리지 않고 LLM 1회로 답한다.
- 팀원에게도 말을 걸 수 있고, 팀장과 팀원의 기억은 섞이지 않는다.
- 비서실장에게 수정을 요청하면 수정안 대신 redirect/escalate 가 나온다. 미참여 부서 직원도 수정안을 내지 못한다 (approve 도 서버가 거절).
- 대화 전용 상한 또는 지시용 예비분에 걸리면 대화가 거절되고, 같은 시점에 지시 세션은 정상 실행된다.
- 새 변경 엔드포인트는 ADMIN_TOKEN 설정 시 토큰 없이 401.
- `npm run verify` 통과, 백엔드 테스트 추가: 수정 적용/되돌리기, find/replace 불일치 처리, 진행 중 세션 거절, 기억 컨텍스트 구성.
