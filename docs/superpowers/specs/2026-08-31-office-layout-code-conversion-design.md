# 사무실 배경 코드 변환 + 구조 재설계

- 상태: 설계 확정, 사용자 검토 대기
- 관련 작업: 캐릭터 디자인 코드 변환(완료), 이동감/카메라, 존 연출, 캐릭터 커스터마이징(모두 완료) 시리즈의 마지막 서브프로젝트

## 배경 및 목표

지금 사무실 바닥·벽·가구는 `Frontend/public/map/office-v2.png` 정적 이미지 한 장이다. `office-map.json`의 방 좌표·문·충돌영역이 그 그림에 픽셀 단위로 맞춰져 있어서, 구조를 바꾸려면 그림을 다시 그려야 한다. 반면 `tiles.png`/`props.png`(바닥타일 7종, 가구 19종)는 이미 절차적으로 생성되지만 런타임에 전혀 쓰이지 않는 죽은 에셋이다. 문(door)은 이미 지금도 정적 배경 위에 코드로 그린다.

목표:
1. 사무실 배경을 코드(빌드타임 생성 스크립트)로 전환해, 손그림 없이 레이아웃을 자유롭게 바꿀 수 있게 한다.
2. 디자인팀에게 전용 방을 주고, 맵을 전반적으로 넓혀 방마다 여유를 준다.
3. 대표실을 비서실·대회의실 사이, 중앙 라운지 바로 위에 배치한다 (사용자 확정).

## 확정된 구조 (사용자 승인)

3행 구조, 중앙 십자 통로:

```
[리서치]  [비서실][대표실]  [대회의실]
[개발] [재무]  (라운지)  [문서] [마케팅]
[기획] [디자인] [로비] [쇼케이스] [카페]
```

- 맨 위 줄: 리서치 · 비서실 · 대표실 · 대회의실이 나란히 — 비서실이 대표실과 대회의실 양쪽 출입을 지키는 자리.
- 대표실은 중앙 라운지와 같은 가로 위치(라운지를 내려다보는 자리)에 둔다.
- 디자인팀은 처음으로 전용 방을 가진다 (지금은 중앙 통로 옆 자리에 임시로 있음).

## 접근 방식: 빌드타임 생성 (런타임 렌더러 변경 최소화)

`generate_sprites.mjs`가 캐릭터를 만드는 것과 동일한 패턴이다.

- **신규**: `Frontend/tools/generate_office.mjs` — `office-map.json`의 zones/doors를 읽어 `tiles.png`/`props.png`를 조합해 `Frontend/public/map/office-v3.png`를 생성한다. `npm --workspace @ai-company/frontend run map:generate`(신규 스크립트, 기존 `map:validate`와 같은 네임스페이스)로 실행.
- **런타임 변경 없음**: `office-renderer.ts`의 `drawFloor()`는 지금처럼 완성된 이미지를 `drawImage()` 한 번으로 그린다. 문·존톤·이름표 등 기존 런타임 연출은 그대로 그 이미지 위에 얹힌다.
- 레이아웃을 바꾸고 싶으면 `office-map.json`(+ 아래에서 설명할 장식 가구 데이터)을 고치고 스크립트를 다시 돌리면 된다 — 손그림 도구가 필요 없다.

이 방식을 고른 이유: 런타임 렌더링 로직에 위험을 새로 들이지 않고, 이미 검증된 캐릭터 생성 패턴을 그대로 재사용한다. 대안(브라우저에서 매번 조립)은 벽 모서리 처리 같은 복잡도만 늘고 지금 당장 얻는 이점이 없다.

## 바닥·벽 렌더링 규칙

- **바닥**: 존 종류별 타일 — `department`는 `floor_wood`, `lounge`/`reception`은 `carpet`, 그 외(entrance/cafe/meeting)는 `floor_tile`. (기존 `drawIdleZoneShade`/`drawZoneTone`이 이미 존 kind 기반으로 연출하고 있어 같은 분류를 재사용한다.)
- **벽**: 각 존의 테두리를 따라 `wall_face`(정면)/`wall_top`(상단) 타일을 단순한 직선 띠로 두른다 — 지금 `drawDoors()`가 문을 그리는 것과 같은 스타일로, 모서리 전용 그래픽 없이 직선만 쓴다. `tiles.png`에 모서리 전용 타일이 없으므로 이게 자연스러운 선택이다.
- **중앙 라운지는 벽을 두르지 않는다** — 지금도 중앙 라운지(소파·안락의자)는 정식 zone이 아니라 그냥 뚫린 통로 위의 장식 가구다. 이 관례를 그대로 유지한다: 라운지는 `office-map.json`의 `zones`에 넣지 않고, 대신 아래 "장식 가구" 데이터에 좌표만 등록해 소파·안락의자·커피테이블을 그린다. (구조 목업의 "라운지" 칸은 위치를 보여주기 위한 것이었지, 벽으로 막힌 방을 의미하지 않았다.)

## 가구 배치 — 두 종류

1. **자동 배치 (책상+의자)**: 이미 있는 좌석 좌표(`zone.seat`, `office-staff.ts`의 `STAFF_SEATS`)마다, 좌석의 `facing` 반대쪽에 책상 프롭을, 그 사이에 의자 프롭을 자동으로 놓는다. 새 좌표를 또 만들 필요가 없다 — 좌석 좌표 자체가 이미 손으로 다듬어진 데이터이므로 그걸 신뢰한다.
2. **장식 배치 (화분·책장·소파·회의테이블·카페 바 등)**: 방마다 몇 개씩 새로 좌표를 잡아 큐레이션한다. 새 데이터 파일 `Frontend/src/data/office-props.json`(또는 `.ts`)에 `{ x, y, type, facing? }[]`로 기록한다.

**충돌**: 자동 배치된 책상은 좌석 좌표 기준 "책상 쪽" 한 칸을 충돌 블로커로 추가한다(현재 `office-map.ts`의 `buildGrid()`가 이미 좌석 좌표는 항상 다시 뚫어주므로, 좌석이 책상 블로커와 겹쳐도 안전하다 — 지금 `STAFF_SEAT_POINTS` 처리와 완전히 같은 패턴). 장식 가구는 각 항목의 실제 폭에 맞춰 블로커를 계산한다.

## 규모 및 좌표

`TILE=32` 유지. 맵을 **82×34 타일**(2624×1088px)로 키운다 (지금 52×30 대비 가로 58%, 세로 13% 확대).

행 배치(y): 위쪽 줄 y1–9(높이9) → 통로 y10–11 → 가운데 줄 y12–20(높이9) → 통로 y21–23 → 아래쪽 줄 y24–32(높이9) → 바깥벽 y33.

중앙 라운지(비정식, 장식 전용): 대략 x32–49, y12–20 범위에 소파·안락의자 2개·커피테이블을 배치 — 지금 화면에 있는 배치를 그대로 확대 이동한다.

### 문 (doors)

각 방은 통로를 마주보는 벽에 문 하나(로비만 둘 — 통로 쪽 + 바깥쪽). 정확한 타일은 각 존 폭의 중앙, 통로 쪽 벽 위에 계산한다 (지금 `office-map.json`이 하는 것과 같은 방식). 구현 시 `validate_office_map.mjs`가 문 좌표가 실제 벽 위에 있는지 계속 검증한다.

### 좌석·회의석·스폰

- **부서 좌석**: 팀장 1 + 팀원 2 = 방마다 3자리. 문에서 먼 벽을 등지고 가로로 나란히, 방 폭 중앙 정렬 — 지금 `STAFF_SEATS`가 쓰는 것과 같은 규칙이다. 정확한 좌표는 구현 중 각 방의 최종 `x,y,w,h`에서 계산한다(공식화된 규칙이라 손으로 하나씩 다시 잡을 필요가 없다).
- **회의 좌석 9석**: 새 대회의실(22×9)의 긴 테이블 둘레에 지금과 같은 상대 배치를 확대해 재배치.
- **스폰/대표 좌석**: 스폰은 로비 안쪽, 대표 좌석 마커는 대표실 안쪽.
- **휴게·잡담 스팟(`LEISURE_POINTS`/`CHAT_SPOTS`)**: 지금은 절대 좌표로 하드코딩돼 있는데, 이번에 **zone 기반 동적 계산으로 바꾼다** — `kind==='cafe'`인 존, 그리고 라운지 장식 구역 안에서 걸을 수 있는 타일을 골라 쓰도록 헬퍼 함수를 하나 추가한다. 레이아웃이 또 바뀌어도 좌표를 다시 손으로 잡을 필요가 없어진다 (이번 작업이 남기는 부수적 개선).

## 마이그레이션 범위 (변경 파일)

## 리스크 / 트레이드오프

- 좌표 데이터 양이 많아 처음 구현 후 몇 차례 브라우저 확인·조정이 필요할 가능성이 높다 (기존 4개 서브프로젝트에서도 항상 실제 렌더링으로 확인 후 다듬었다).
- 벽에 모서리 그래픽이 없어 직선 띠로만 표현 — 미적으로 지금 손그림보다 단순해진다 (이미 캐릭터 변환에서 감수하기로 한 것과 같은 트레이드오프).
- 라운지를 비정식(벽 없는) 구역으로 유지하기로 해, 향후 "라운지도 완전한 방으로" 요청이 오면 별도 작업이 필요하다.
